# 作品データを折り図(見本)と突き合わせる作業指示

**目的**: `src/models/*.ts` の作品について、**おりがみくらぶの折り図(=見本)と
折り方が一致しているか**を1作品ずつ検証し、相違があれば**見本に忠実になるよう直す**。

見た目が似ていることは合格の条件ではない。**工程の順番・折り線の位置・どの層を折るか・
どちら側(手前/うしろ)へ折るか**が見本と同じであることを見る。過去にこのリポジトリで
起きた不具合は「折り図を見ずに作った結果、見た目は近いが手順が別物」というものが
ほとんどで、その修正履歴は `CLAUDE.md` に全部残っている。

---

## 1. 最初にやること

1. `CLAUDE.md` を最初から最後まで読む。作品ごとの折り線の根拠・既知のハマりどころ・
   **決定済みで蒸し返さない事項**が書いてある。ここを読まずに直すと必ず衝突する。
2. `README.md`(エンジンの考え方)と `src/engine/types.ts`(工程データの型)を読む。
3. ビルドと起動を通す。

   ```bash
   npx tsc -b && npm run dev
   ```

4. ナビ画面には検証用フックがある(E2E用)。ブラウザのコンソールから:

   ```js
   window.__origami.setT(3)        // タイムラインを工程3の直後へ
   window.__origami.getPositions() // 全頂点の [x,y,z](折り後の座標)
   window.__origami.getModel()     // 頂点・面・工程データ
   ```

## 3. 道具

### 折り図を落として実測する

```bash
# 画像名は zu.html から取る(フォルダ名と違うことがある)
curl -s https://www.origami-club.com/easy/vehicle/yacht/zu.html | grep -o 'rn-image/zu/[a-z0-9-]*\.gif'

node tools/zu-measure.mjs fetch yacht           # tools/.zu/yacht.{png,bmp} ができる
node tools/zu-measure.mjs map tools/.zu/yacht.bmp            # パネルの位置を俯瞰
node tools/zu-measure.mjs bbox tools/.zu/yacht.bmp 30 245 245 445   # 色の面/線の外接矩形
node tools/zu-measure.mjs runs tools/.zu/yacht.bmp 30 245 245 445   # 行ごとの色の区間
node tools/zu-measure.mjs outline tools/.zu/yacht.bmp 30 245 245 445 8
node tools/zu-measure.mjs probe tools/.zu/yacht.bmp 30 245 245 445 r350,c222
```

`tools/.zu/*.png` は Read ツールで開いて目で見る用。**パネルを1枚ずつ拡大して見ること**
(`sips -c <高さ> <幅> --cropOffset <y> <x>` で切り出し、`sips -Z 900` で拡大)。

### 実測で気をつけること(過去に何度もハマっている)

- GIF の透明部分は BMP で alpha=0 になる。**透明を黒と誤判定しない**(道具側で対処済み)。
- **パネルごとに縮尺が違う**。1枚から出した数値を信じない。別パネルと完成図で必ず裏を取る。
  (例: ぺんぎんは同じ寸法がパネル❹から 0.207、パネル❺から 0.106 と出た)
- 折り図は手描き。**目印(1/2・1/3・角の二等分線・「辺にちょうど重なる」など)に
  一致するなら厳密値を採る**。実測はその裏づけ。
- 折り図では、重なった同じ位置の2本のふちを**わざと少しずらして描く**ことがある。
  輪郭の小さな「折れ」を本物の頂点だと思わないこと(ヨットで一度ハマっている)。

## 4. 1作品あたりの手順

### A. 見本の工程を書き出す

折り図のパネル❶❷❸… を一つずつ見て、**「何を」「どの線で」「どちらへ」折るか**を
文章にする。「うらがえす」「むきをかえる」も1工程として数える。

### B. アプリの工程と対応づける

`src/models/<id>.ts` の `steps` と突き合わせ、**過不足がないか**を見る。よくある相違:

- 見本にある「折り目をつけて戻す」工程が無い
- 見本の2段階の折り(例: つのを折り上げ→開く)を1回にまとめている
- 見本と順番が違う / 最後の「うらがえす」が無い
- 「上の1枚だけ折る」ところを全部の層で折っている(逆も)

### C. 折り線を実測して照合する

各工程の折り線について、見本のパネルから座標を出し、モデルの値と比べる。
紙は `[-1,1]` の正方形(またはひし形)に正規化して比較する。

### D. アプリ側を数値で実測する

```js
window.__origami.setT(k);  window.__origami.getPositions()
```

**「角が○○にちょうど来る」という見本の目印は、必ずこれで確認する。**
例(実際に使った検証):

- ヨット: ❷で角が斜辺上の `(1-√2, 1-√2)` に着地するか
- ぺんぎん: ❺で紙の左右の角が中心を越えて `x=∓0.2` に来るか、❻で `±0.6` まで出るか
- ろけっと: ❹で上の角が中心線上の `(0,-0.5)` に来るか、❻で尾翼が `±2/3` まで出るか

### E. 完成形を照合する

1. **縦横比**: 折り図の完成図パネルの外接矩形(`bbox`)と、アプリの完成形
   (`setT(99)` → `getPositions()` の x/y の最大最小)の比を比べる。
   10%以上ずれていたら折り線の角度が違う可能性が高い(ねこ・きつね・くまで実例あり)。
2. **色の出方**: どの面が表/裏の色になるかを比べる。層順の誤りは色に出る。
3. **各工程の途中の形**: ナビ画面の工程一覧に出る折り図サムネイル(各工程の「折る前」)を
   折り図のパネルと並べて見ると、ずれている工程がすぐ分かる。

## 5. 「相違」の判定と扱い

| 段階 | 例 | 扱い |
|---|---|---|
| **A. 折り方の相違** | 工程の過不足・順番違い・折る層が違う・折り線の位置が目印から外れている | **直す**(最優先) |
| **B. 幾何のずれ** | 折り線の角度が実測と 5% 以上違う、完成形の縦横比が 10% 以上違う | **直す** |
| **C. 見た目の粗** | 層の前後で細い色のはみ出しが1〜2px 残る | 記録するだけ(実用上許容。§6) |

判断に迷ったら**直さずに報告**する。特に「直すと他の工程の層順が変わる」ものは、
影響範囲を書いて相談すること。

## 6. 直してはいけない/勝手に変えない(決定済み事項)

- **くじらの色**: 原典は完成形が紙の裏の色になるが、アプリは「動かない側が常に表を向く」
  方針(白が前に出る不具合を防ぐ)を優先して表の色にしている。2026-08-09 にユーザー判断で
  確定済み。**再検討しない。**
- **手裏剣の中央のわずかな白のぞき**: 180°未満で畳むエンジンの層順の限界。許容と決定済み。
- **ヨットの完成形が 7.3° 傾く**: 折り図❹は船底が水平になるよう回して描いてあるだけで、
  折り自体は❸で終わり。回す工程を足さない。
- **「たてよこの折り目」を片方だけにしている作品**(ひよこ・ぺんぎん・ろけっと):
  もう片方が以降の折り線そのもの、または目安にしか使われない場合は意図的に省いている。
  省いた側が実際に折り線として使われているなら相違として報告すること。
- **紙の色**: 折り図の実測値を使う方針。デザイン都合で変えた作品(ぱんだの白黒など)は
  CLAUDE.md に理由がある。

## 7. 直すときの原則

1. **見本に忠実に**。「見た目を合わせるための独自手順」は禁止。過去の作り直しは全部
   これが原因(犬・ぱんだ・くま・チューリップ・兜・うさぎ)。
2. 折り線は**目印から出した厳密値**を第一候補にする(例: `3-2√2`、`(1-F)/2`、`y=-1/3`)。
   実測値しか根拠がない場合は、コメントに実測値と出典パネルを書く。
3. 座標の根拠・層順の理由を**モデルファイルの先頭コメントに日本語で書く**
   (既存ファイルの書式に合わせる)。
4. 直したら `CLAUDE.md` の当該作品の項目を更新する。**新しいハマりどころは必ず追記**。
5. 1作品 = 1コミット。コミットメッセージには「何が見本と違ったか」「どう直したか」を書く。

### 既知のハマりどころ(直す前に必ず読む)

- **折り目の軸に、前の工程で動いた頂点を使わない**。z 方向に軸が傾き、フラップが
  奥へ回って真っ白に見える(ぱんだ・ぺんぎんで再発)。軸は「その時点で z=0 の頂点」で取る。
- **「折って開く」の戻しの符号**。直前の valley の自動符号が -1 のとき、戻しも -1 だと
  4°傾いたまま残る。`setT` で「折る前」と「戻した直後」の全頂点距離が 0 になることを確認する。
- **層順は残差角の階段で作る**(例 176°/173°)。同じ角度だと z 差が 0.001 しかなく、
  意図しない層が前に出る(ろけっとで実例)。それでも足りなければ面ごとの複製頂点+z補正。
- **複製頂点**: ある面だけを動かしたい/沈めたいときは、その面専用の頂点を複製する。
  共有したままだと隣の面まで引きずられる。
- **平面でない四角形**は三角形分割の対角線が左右で非対称になる。鏡写しで明示的に2枚に割る。

## 8. 検証(直したあと必ず)

```bash
npx tsc -b            # 型
npx oxlint src        # 既存の警告4件(react の fast-refresh)以外を増やさない
npm run dev           # 画面で全工程を再生
```

数値の確認(コンソール):

- 各工程の目印(角がどこに来るか)が見本どおりか
- 「折って開く」の打ち消しが 0 か
- 完成形の縦横比が折り図の完成図と一致するか
- 全工程で紙が破れていないか(共有すべき頂点が離れていないか)

## 9. 報告フォーマット

作品ごとに、次の形で報告する(直した/直していないに関わらず全作品ぶん)。

```
### <id> <名前>
- 見本: <URL>
- 工程の対応: 見本❶→app1, ❷→app2 … (過不足があればここに)
- 折り線の照合: 工程ごとに「見本の実測値 / モデルの値 / 判定」
- 完成形: 縦横比 見本 x.xx / アプリ x.xx、色の出方の一致
- 判定: 一致 / 相違あり(段階A・B・C)
- 対応: 直した(コミット hash)/ 直していない(理由)
```

最後に「相違があった作品の一覧」と「未解決の疑問」をまとめる。
